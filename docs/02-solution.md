# 02 - 方案（Solution）

设计方法遵循"通用 Agent 设计方法论"三板斧推导：**先拆材料与能力入口，再编排推理循环，最后定义评测与回流**。

## 一、调用流程

```text
用户请求（input.json：question + history?）
  └─> CLI（src/main.py：输入文件校验，非法 JSON 非零退出）
        └─> ReAct 循环（src/agent.py，步数上限默认 12）
              ├─ 模型决策（src/model_client.py：Mock 策略 / OpenAI 兼容 API 双入口）
              │     动作 = tool_call(name, args) 或 finish(payload)
              ├─ 工具执行（src/tools.py：search_docs / read_doc，均为只读）
              │     观察结果（含异常转观察，错误恢复不终止循环）
              ├─ Trace 记录（src/trace.py：步骤/参数/返回摘要/决策依据）
              └─ 循环直到 finish 或达到上限（返回 incomplete）
```

典型路径为 2 次工具调用 + 1 次 finish：`search_docs → read_doc（top1）`；冲突场景多读一篇：`search_docs → read_doc(D01) → read_doc(D02)`；资料外场景检索两次（改写词 + 原始问句）。

## 二、动态决策（ReAct 循环的核心）

模型不是走固定分支，而是根据**最近一次工具观察**调整下一步：

| 观察结果 | 下一步动作 | 最终状态 |
| --- | --- | --- |
| 缺 question | 直接结束并列出缺口，不调用工具 | `missing_input` |
| 尚未检索 | 改写检索词（省略式追问结合上文）→ `search_docs` | — |
| 检索为空（第一轮） | **改用原始问句补充检索一次** | — |
| 两轮检索均为空 | 如实返回资料外与缺口，不编造 | `out_of_scope` |
| 检索命中，尚未读原文 | 按相关度逐篇 `read_doc`（最多 2 篇）——**引用必须基于原文，不用 snippet 作答** | — |
| 原文读取完毕，多篇对同一问题陈述不同数值且无适用范围/优先级说明 | **列出冲突与双方引用，请求确认适用制度**，不擅自选答案 | `needs_confirmation` |
| 原文读取完毕，单篇或陈述一致 | 依据最相关文档的原文回答，逐字引用 | `answered` |
| 读取的原文中缺少支持回答的陈述 | 如实终止并说明缺口 | `incomplete` |
| 工具失败（failed/tool_error） | **重试同一步骤一次**；连续 2 次失败则如实终止 | `failed` |
| doc_not_found | 如实终止（重试无意义） | `incomplete` |

这些分支由**观察结果驱动**而非预设脚本：同一策略函数，单文档直接回答（normal）、双文档冲突请求确认（doc-conflict）、两轮检索未命中返回缺口（out-of-scope）、省略式追问结合上文改写（followup）、注入故障先失败再续跑（tool-failure）——Trace（`examples/*.trace.json`）中每步的 `observation` 与 `decision_basis` 记录了"为什么走这条路"。

## 三、模块职责（对应第二板斧五模块）

| 模块 | 职责 | 边界 |
| --- | --- | --- |
| Prompt（`prompts.py`） | 任务边界、引用纪律、冲突处理、追问处理、输出契约 | 不承载长期流程与全部背景 |
| Agent Loop（`agent.py`） | 观察-行动循环、停止条件（finish / 步数上限）、错误恢复（异常转观察） | 不含业务判断，判断归模型 |
| Memory | 任务内状态：历史观察即记忆；对话历史（history）随任务输入用于追问改写 | 不做跨请求长期记忆 |
| Skill | 不沉淀——一次性任务，流程未稳定重复 | — |
| Tool（`tools.py`） | 2 个原子工具：文档检索/片段读取 | 不承载完整业务流程 |

**为什么不上多 Agent**：任务无并行子任务、无权限隔离需求、上下文短，单 Agent + 工具足够；按"单 Agent 失效信号"逐条检查均不命中。

## 四、技术取舍

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 框架 | **原生实现**（不用 LangGraph/ADK 等） | 核心 Loop 仅 ~40 行，原生实现最透明、依赖为零，且避免"用框架默认行为代替设计解释" |
| 语言 | Python 3.10+ 标准库 | 零第三方依赖，评审可在隔离环境直接运行；API 模式用标准库 urllib 调 OpenAI 兼容接口 |
| 模型入口 | Mock（默认）+ API 双路径 | 无 Key 时全链路可离线验证；**Mock 边界：以"任务+历史观察"为输入的策略函数，验证 ReAct 流程与工具协议，不证明真实模型效果** |
| 检索实现 | 中文 2-gram 重合度打分 + 标题加权（工具层） | 模拟真实检索引擎的关键词容错与排序；检索改进（改写/补充检索）的**决策**留给模型侧，与真实 RAG 的职责划分一致 |
| 运行方式 | CLI | 最贴合测试自动化与 Trace 落盘；界面/HTTP 非必需 |
| 材料接入 | 本地 JSON + 工具按需读取 | 文档量小（5 篇）且需精确 doc_id 引用，不需要向量库/RAG；单进程本地工具，不需要 MCP |

## 五、权限与安全边界（第一板斧：模型不是安全边界）

- **引用真实性（结构保证）**：citations 的 quote 从 `read_doc` 返回的原文中按句切分提取，`snippet` 只用于检索排序与决策——"用摘要冒充原文"在数据流上不可能发生；测试对每条引用断言 `quote ∈ 文档 content`。
- **事实与判断分离（本题关键设计）**：工具只返回文档事实（标题/版本/日期/原文），**不判断文档之间是否冲突**；读取多篇原文后的数值陈述比较、冲突认定、是否请求确认，全部由模型完成——若工具层替模型判冲突，"查证"就成了预设分支。
- **答案从原文推导**：回答直接引用相关句原文、冲突值用正则从相关句提取（`30 天` vs `15 天`）、"未说明适用范围与优先级"由检查原文是否含"适用/优先"字样得出——**替换文档内容，答案与动作随之改变**（测试 `test_8` 直接覆盖审核要点）。
- **无依据不编造**：策略上两轮检索未命中或原文无相关陈述时返回 `out_of_scope/incomplete` 与缺口；结构上回答文本只由原文片段组装，不存在编造通道。
- **故障注入**：`inject.search_fail_once` 由输入显式声明（注入一次失败、重试成功），用于确定性复现工具失败验收场景。
- **审计**：全部工具调用（含参数与返回）进入 Trace。
