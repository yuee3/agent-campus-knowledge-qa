# 04 - AI 使用（AI Usage）

> 本文档如实记录 AI 辅助的范围、个人贡献与验证方式。评审者可对照 git 历史与 Trace 交叉验证。

## AI 辅助的范围

本项目在 AI 辅助工具（编码智能体）支持下完成，具体分工如下。

**AI 承担的部分**

- 依据候选人的设计方案生成项目脚手架与全部代码：工具层（2-gram 检索打分、单次故障注入）、ReAct 循环、Mock/API 双模型入口、CLI、Trace 记录
- 生成 6 个验收场景的测试代码与合成知识库（5 篇带版本日期的制度文档，含参考实例的 D01/D02 冲突对）
- 生成 examples/ 的实际运行输出、Trace 与测试记录
- 起草 docs/ 五篇文档与 README

**候选人承担的部分**

- 题目理解与验收标准确认：把题目 6 个必验收点 + 审核要点（引用支持回答、替换文档内容核对答案与动作、冲突处理、无依据回答属关键缺陷）转成可断言的成功标准
- 核心设计决策（见 [02-solution.md](02-solution.md)）：
  - 选定"原生实现 + CLI + Mock/API 双入口"的技术路线与边界声明
  - **事实与判断分离**：search/read 只返回文档事实，冲突查证、是否足以回答、是否请求确认全部留在模型侧——保证"列出冲突并查证，不凭空选一个答案"是真实的动态决策
  - 引用纪律的结构保证：quote 从 read_doc 原文按句提取，snippet 只用于决策，杜绝"摘要冒充原文"
  - 答案与冲突值从原文推导（换文档内容即随之改变），追问时结合上文改写检索词
- 设计评审与修正：修正生成脚本残留的乱码表达式；确认追问场景的检索词只取本轮核心词（避免把上文主题词并入检索导致 D03/D04 被误判为冲突）
- 逐项验证（见下节）
- 本文档及各文档的核对修订

## 验证方式

AI 生成的产物不默认可信，按以下方式验证：

1. **自动化测试**：`python -m unittest discover -s tests -v`，11 个用例覆盖 6 个必验收点 + 步数上限 + 内容替换鲁棒性 + CLI 边界，实际结果见 [examples/test-results.txt](../examples/test-results.txt)。
2. **红线核对**：对全部场景断言引用逐字属于原文、冲突不擅自选答案、无依据不编造（`tests/test_acceptance.py::assert_red_lines`）。
3. **Trace 抽查**：人工核对 `examples/*.trace.json`，确认每步工具参数、观察结果与决策依据一致，无跳步（如未读原文就作答、未查证冲突就选边）。
4. **参考实例对拍**：用题目参考实例（D01 30 天 vs D02 15 天 → 列出冲突与引用并请求确认，不擅自回答）作为金标准用例复现，见 `examples/doc-conflict.*`；"只检索到 D01 且无冲突时依据 D01 回答"见 `tests/test_8` 删除 D02 后的断言。
5. **审核要点专项**：`test_8` 替换文档内容（30→45 天、删除 D02），断言答案与动作随之改变，证明无场景硬编码。
6. **可复现性**：评审者按 README 命令从零运行，应得到与 examples/ 一致的结果（run_id 与时间戳除外）。

## 边界声明

- 仓库内不包含任何真实密钥；`.env.example` 仅列出变量名。
- Mock 模型是离线确定性策略，**它验证的是 ReAct 流程与工具协议，不证明真实模型效果**——这一边界同样适用于 examples/ 中的全部运行记录。
